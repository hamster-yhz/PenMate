# PostgreSQL 18 Full Migration Implementation Plan

**Goal:** Replace every MySQL/MariaDB runtime, SQL dialect, migration, test fixture, and deployment reference with PostgreSQL 18.4, while rebuilding the database history as a clean seven-version Flyway baseline.

**Architecture:** PostgreSQL becomes the only relational database. Production and Docker use `postgres:18.4-alpine`; local development uses the installed PostgreSQL 18.4 service. Persistent JSON uses `jsonb`, persisted timestamps use `timestamptz(3)` and Java `Instant`, and application-level Snowflake business IDs remain unchanged. Existing database data is intentionally discarded; no cross-database data migration is implemented.

**Tech Stack:** PostgreSQL 18.4, Spring Boot 3.3, Java 21, MyBatis 3, Flyway 10, Testcontainers PostgreSQL, Docker Compose, GitHub Actions.

**Implementation Status (2026-07-19):** Tasks 1-10 are implemented. Full local PostgreSQL verification (506 backend tests), backend packaging, JAR driver inspection, 170 frontend tests, frontend build, YAML parsing, and active-source scans pass. Testcontainers and Docker Compose runtime resolution are delegated to CI because Docker tooling is unavailable on this workstation.

---

## Confirmed Decisions

- Existing MariaDB/MySQL data does not need to be preserved.
- Local, CI, Docker, and production target PostgreSQL 18.4.
- Docker service names become `postgres`; the volume becomes `postgres-data`.
- The old Flyway history is replaced with seven new PostgreSQL migrations.
- H2 and all MySQL compatibility modes are removed.
- Internal `id` columns use `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Business IDs remain application-generated `BIGINT` Snowflake values.
- Physical foreign keys are not added; existing logical relationships remain application-managed.
- Logical relationship columns keep appropriate indexes and business IDs keep unique constraints.
- Structured JSON columns use PostgreSQL `jsonb` with an explicit MyBatis type handler.
- Persisted timestamps use `timestamptz(3)` and Java `Instant`.
- API timestamps use ISO-8601 UTC values with a `Z` suffix.
- Email and selected code fields use explicit normalization and `lower(...)` indexes instead of global case-insensitive collation.
- Production bootstrap secrets come from environment variables.
- Local bootstrap placeholders live in `application-local.yml` and may be edited by the developer.
- Bootstrap defaults to create-only; `BOOTSTRAP_RECONCILE=true` explicitly enables updates.
- Production Flyway uses `baseline-on-migrate=false` and requires an empty database.
- Local integration tests use a separate `penmate_test` PostgreSQL database.
- CI integration tests use PostgreSQL 18.4 Testcontainers.
- Production Flyway seeds only required system metadata. Demo book/Story Bible/Agent cases remain test-only.
- Windows PowerShell and Linux Bash demo seed/cleanup scripts are provided.
- CI/CD must not delete volumes, reset databases, run data migration, or perform destructive cutover actions.
- The old MariaDB container and volume are removed manually by the operator.

## Out Of Scope

- Migrating existing MariaDB data into PostgreSQL.
- Adding physical foreign keys.
- Renaming domain tables or changing public business IDs.
- Redesigning API resources unrelated to timestamp serialization.
- Automatically deleting `penmate_mysql-data` from CI/CD.
- Supporting MySQL, MariaDB, or H2 after migration.

## Acceptance Criteria

- A fresh PostgreSQL 18.4 database migrates from V1 through V7 without manual SQL repair.
- The backend starts with `org.postgresql.Driver` and no MySQL/MariaDB driver in its JAR.
- Docker Compose contains no active `mysql`, `mariadb`, port `3306`, or MySQL volume references.
- Active application and test SQL contains no MySQL-only DDL/DML.
- No H2 dependency or `MODE=MySQL` test remains.
- All persisted JSON fields round-trip through JSONB.
- All persisted event/audit timestamps are `timestamptz(3)` and Java `Instant`.
- Public timestamps include an explicit UTC offset (`Z`).
- One administrator and one default model configuration are bootstrapped idempotently from environment variables.
- Demo book/Story Bible/Agent Case data is never loaded by production Flyway.
- Local tests can use `penmate_test`; CI uses PostgreSQL 18.4 Testcontainers.
- CI/CD performs no destructive database or volume operation.
- The final push contains a complete PostgreSQL-only revision rather than an intermediate hybrid state.

## Manual Production Cutover Boundary

The operator, not CI/CD, is responsible for stopping/removing the old MariaDB service and deciding when to delete `penmate_mysql-data`. The new Compose definition creates `penmate_postgres-data`. The old volume should remain until PostgreSQL startup, Flyway migration, bootstrap, authentication, model configuration, and core API smoke tests have been verified.

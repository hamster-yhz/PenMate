# PenMate 统一全量后台后端技术方案 v1.0

> 基于 [`统一全量后台-表结构设计-v1.1.md`](docs/project-specifications/backend/统一全量后台-表结构设计-v1.1.md)、[`统一全量后台-接口设计-v1.1.md`](docs/project-specifications/backend/统一全量后台-接口设计-v1.1.md)、[`DDD架构规范.md`](docs/project-specifications/backend/DDD架构规范.md) 制定实现级技术方案。

## 1. 目标与范围

- 目标：将“统一全量后台”的数据与接口设计落为可实施的 Spring Boot + DDD 后端工程。
- 范围：
  - IAM/RBAC、小说业务域、Agent 审批域、文风/插件/BYOK/RAG 域。
  - 混合存储（MySQL + Object Storage + Vector DB）。
  - 最小可上线闭环：审批流（提案->审核->执行）与章节对象化存储。

---

## 2. 技术选型

## 2.1 核心框架
- Java 21
- Spring Boot 3.3.x
- Spring Web + Validation
- MyBatis（持久层框架，SQL可控）
- Flyway（DDL迁移）

## 2.2 存储与中间件
- MySQL 8（事务主库）
- Redis（JWT denylist、权限缓存、幂等）
- S3 兼容对象存储（MinIO/S3/COS/OSS）
- 向量库（Milvus/Pinecone）
- RabbitMQ（承载 outbox 异步投递）

## 2.3 工程能力
- OpenAPI 3.0（接口契约）
- Micrometer + Prometheus（指标）
- OpenTelemetry（链路）
- JUnit5 + Testcontainers（集成测试）

## 2.3.1 小项目轻量化建议
- 接口契约：保留 OpenAPI 3.0（低成本高收益）。
- AI编排：按需使用 LangChain4j（用于 Agent/tool 调用，不替代 OpenAPI）。
- 可观测性最小集：
  - 保留 Spring Boot Actuator 基础健康检查。
  - 指标先用 Micrometer 本地日志/JVM 指标，不强制立即上 Prometheus。
  - 暂不接入 OpenTelemetry，全链路追踪放到二期。
- 测试：先保留 JUnit5；Testcontainers 在接入 CI 或跨环境不一致时再启用。

## 2.4 组件用途与接入方式

### Flyway
- 干嘛：管理数据库结构版本，保证环境表结构一致。
- 怎么用：
  - 在 `resources/db/migration` 放 SQL 迁移文件。
  - 命名遵循 `V{版本号}__{描述}.sql`。
  - 应用启动自动执行未执行迁移。

### OpenAPI 3.0
- 干嘛：把 REST 接口变成标准契约，可生成文档和SDK。
- 怎么用：
  - 在 Controller 增加接口注解。
  - 启用 `/v3/api-docs` 与 Swagger UI。
  - 评审与联调以 OpenAPI 文档为准。

### LangChain4j
- 干嘛：做 LLM 对话编排、工具调用、记忆与 RAG 集成。
- 怎么用：
  - 在 Agent 相关应用服务中接入模型客户端与 Tool 路由。
  - 让模型只产出提案或调用受限工具，不直接越过审批写库。
  - 与审批接口配合，实现 Human-in-the-loop。

### Micrometer + Prometheus
- 干嘛：采集业务与系统指标，用于可观测和告警。
- 怎么用：
  - 暴露 `/actuator/prometheus`。
  - Prometheus 定时抓取。
  - Grafana 配仪表盘与告警规则。

### OpenTelemetry
- 干嘛：链路追踪，定位慢请求和跨服务调用问题。
- 怎么用：
  - 引入 OTel SDK 或 Java Agent。
  - 自动注入 TraceId/SpanId 到日志。
  - 导出到 Jaeger/Tempo/OTel Collector。

### JUnit5 + Testcontainers
- 干嘛：真实依赖环境的自动化测试，降低“本地可跑线上失败”。
- 怎么用：
  - JUnit5 组织单元与集成测试。
  - Testcontainers 启动 MySQL、RabbitMQ、Redis 等容器。
  - CI 中执行集成测试后再发布。

```text
    rag/
  infrastructure/
    persistence/

    vector/
    messaging/

```

分层职责遵循 [`DDD架构规范.md`](docs/project-specifications/backend/DDD架构规范.md)：
- `interfaces`：Controller、DTO、参数校验、响应封装。
- `application`：用例编排、事务边界、权限编排。
- `domain`：聚合根、领域服务、仓储接口、领域事件。
- `infrastructure`：DB/对象存储/向量库/MQ适配实现。

## 4. 关键技术设计

## 4.1 混合存储策略
- 元数据写 MySQL（章节、版本、审批、索引状态）。
- 正文/快照写对象存储，MySQL 仅保存 `object_key/etag/size/checksum`。
- RAG 切片索引关系写 MySQL，embedding 写向量库。

## 4.2 一致性模型
- 强一致：单请求内 MySQL 事务。
- 最终一致：对象存储与向量库通过 outbox + worker 补偿。
- 幂等：写接口要求 `Idempotency-Key`，并在 Redis/DB 防重。

## 4.3 Human-in-the-loop 审批闭环
1. Agent 只提交“变更提案”，落 `agent_approval_requests`（pending）。
2. 前端展示审批卡片。
3. 用户点击同意 -> 调用审批接口。
4. 后端以用户身份执行受控写操作并记录 `agent_approval_actions` + `ops_audit_logs`。

## 5. 模块实现顺序（建议）

## 5.1 里程碑 M1（基础可运行）
- 工程初始化、统一异常、统一响应。
- Flyway 首版迁移：IAM + novel 核心 + approval 核心表。
- 审批 API 最小闭环：create/list/approve/reject。

## 5.2 里程碑 M2（混合存储）
- 章节对象化上传/提交（签名 URL + commit）。
- 章节版本快照对象化。
- `storage_objects` 与对象回填任务。

## 5.3 里程碑 M3（RAG 与异步）
- RAG 文档上传、parse/embed/index-status。
- outbox 投递 + worker 消费 + 向量 upsert。

## 5.4 里程碑 M4（完善与上线）
- RBAC 全权限矩阵接入。
- 压测、审计、告警、灰度发布。

## 8. 安全设计

- JWT：签名验证 + denylist 校验。
- 权限：接口权限码 + 项目成员角色双重校验。
- 密钥：`encrypted_api_key`，严禁日志明文输出。
- 对象存储：私有桶 + 短时预签名 URL。

---

## 9. 可观测性

- 日志：JSON structured logging，关联 `traceId`。
- 指标：
  - 接口 RT、错误率、吞吐
  - 审批积压数
  - outbox 重试次数
  - 向量任务成功率
- 告警：
  - 审批失败率阈值
  - 向量入库失败阈值
  - 对象提交失败阈值

---

## 10. 风险与规避

- 风险：跨存储不一致。
  - 规避：outbox + 幂等重试 + 死信队列。
- 风险：审批绕过前端。
  - 规避：后端强制审批状态机，拒绝未审批写入。
- 风险：大文本写入热点。
  - 规避：正文对象化 + 元数据索引化。

---

## 11. 验收标准

- 能跑通审批最小闭环：提案、列表、审批通过/拒绝、审计可追踪。
- 能跑通章节对象化：上传 URL、commit、读取 URL。
- Flyway 能一键初始化核心表。
- 关键接口符合 [`统一全量后台-接口设计-v1.1.md`](docs/project-specifications/backend/统一全量后台-接口设计-v1.1.md) 约定。

# AI小说Copilot产品需求文档（PRD）v0.3

## 0. 文档信息
- 版本：v0.3
- 日期：2026-04-17
- 目标版本：Agent核心能力一期
- 文档定位：在现有代码基础上，完成核心Agent闭环开发，并落地可运行、可观测、可验收的技术方案。

---

## 1. 背景与现状诊断

### 1.1 背景
v0.2 已定义「Agent主写作 + 人在回路审批 + 插件 + 文风 + RAG」的完整愿景，但当前代码实现仍处于“模块骨架可用、智能编排未打通”的阶段，需要通过一期研发实现最小可用闭环（MVP）。

### 1.2 当前代码现状（问题清单）
1. **Agent Loop未实现**：生成任务创建后立即从 `running` 置为 `done`，仅发送固定token，缺少真实LLM推理与多轮工具调用。
2. **LangChain4j未接入**：后端依赖与调用链中未发现 `AiServices` / `@Tool` / `ChatLanguageModel` 等实际实现。
3. **前端流式链路未打通**：虽有SSE接口地址构造，但工作区仍以轮询为主，未消费SSE流。
4. **状态枚举不一致**：后端状态为 `done/applied/failed`，前端轮询终止条件使用 `SUCCEEDED/FAILED/ERROR/CANCELLED`，存在行为偏差风险。
5. **RAG/插件/审批未串联进生成主链路**：当前更多是独立管理API，未进入Agent执行编排。
6. **模型密钥“加密”能力不达标**：当前为占位式封装（逻辑层字符串包装），不满足真实安全要求。

### 1.3 根因总结
- 先行完成了领域模型与接口层，未完成“编排内核”。
- 缺乏统一的Agent状态机、事件协议和端到端验收标准。
- 前后端围绕“流式生成”的契约未统一（状态、事件、终止条件）。

## 2. 一期目标与成功定义

### 2.1 一期核心目标（P0）
在不推翻现有架构的前提下，完成以下闭环：

**用户输入指令 -> Agent检索上下文（大纲/章节/文风/RAG）-> 可选工具调用（插件）-> 流式输出 -> 识别结构化变更触发审批 -> 用户审批 -> 写回结果并同步面板**。

### 2.2 成功定义（DoD）
1. Workbench 进入真实流式输出（非伪流）。
2. Agent生成链路可执行：至少支持“纯生成”和“单工具增强生成”两类路径。
3. 至少1条HITL审批场景可跑通（如“新增世界设定卡片”）。
4. RAG可参与生成前检索并产出可追踪日志。
5. 前后端状态机统一，轮询逻辑可下线或降级为兜底。
6. 关键指标可观测（成功率、耗时、失败原因、token/成本统计）。

## 3. 范围与边界

### 3.1 本期范围（In Scope）
- Agent编排内核（后端）
- LangChain4j接入与基础Tool体系
- 流式输出（SSE主通道）
- RAG检索接入生成链路
- 插件调用接入生成链路（先支持执行型Tool）
- 审批卡片自动触发与确认回写（最少1类实体）
- 前端Agent面板状态机改造
- 安全加固（API Key真实加密存储）
- 端到端测试与可观测体系

### 3.2 非本期范围（Out of Scope）
- 多Agent协作/长时自治任务
- 复杂规划器（树搜索、反思链、多策略路由）
- 全量插件生态治理（评分、市场审核）
- 企业级多租户计费系统

### 3.3 分期策略
- P0：核心闭环可用
- P1：质量与扩展性增强（更多Tool类型、上下文策略优化）
- P2：高级规划能力与成本治理

## 4. 角色与关键用户故事

### 4.1 角色
- 作者（普通用户）
- 审批执行者（通常为作者本人或协作者）

### 4.2 用户故事
1. 作为作者，我希望输入章节写作指令后，能看到实时流式生成并一键合并至编辑器。
2. 作为作者，我希望Agent自动参考当前文风和历史设定，减少风格断裂。
3. 作为作者，我希望当Agent发现新设定时先弹审批卡，不直接落库。
4. 作为作者，我希望开启插件后Agent可自动调用工具增强内容准确性与趣味性。

## 5. 功能需求（业务）

### 5.1 Agent对话与生成
1. 支持创建会话、发送消息、创建生成任务。
2. 生成任务需支持状态流转：`pending -> running -> waiting_approval -> done/applied/failed/cancelled`。
3. 生成过程按token或chunk流式回传。
4. 支持“合并到编辑器尾部/替换选区”的前端交互。

### 5.2 上下文与记忆（RAG）
1. 生成前自动汇聚上下文：最近会话、当前章节、大纲摘要、默认文风。
2. 可选调用RAG检索并注入结果片段。
3. 记录检索日志（命中条数、来源、耗时、是否被采纳）。

### 5.3 插件工具（Tool）
1. 仅启用项目已安装且可用的插件Tool。
2. Tool调用必须落日志（请求摘要、响应摘要、耗时、状态）。
3. Tool异常不应导致整条链路崩溃，需可降级继续生成。

### 5.4 HITL审批
1. 对高风险写操作（如新增/更新角色或世界设定）产出审批请求。
2. 任务进入 `waiting_approval` 时前端可见审批卡。
3. 用户审批通过后执行落库并继续/完成任务；驳回后给出可继续创作文本。

### 5.5 文风控制
1. 每次生成必须注入文风约束（系统提示）。
2. 中途切换默认文风时给出全局警告并记录切换日志。

### 5.6 模型与BYOK
1. 支持项目策略路由到用户可用模型配置。
2. API Key需真实加密存储并可轮换。

## 6. 非功能需求

### 6.1 性能与体验
- 首Token时延（TTFT）P95 <= 2.5s（内网/开发环境可放宽）。
- 生成链路成功率 >= 95%（P0阶段）。
- SSE断连可自动重连一次并给出状态提示。

### 6.2 一致性与可靠性
- 任务状态变更可追踪、幂等。
- 审批动作具备乐观并发保护，避免重复执行。

### 6.3 安全与合规
- API Key采用KMS/AES-GCM等真实加密方案，不允许明文或伪加密。
- 检索与会话数据按项目/用户隔离。

### 6.4 可观测性
- 指标：任务数、成功率、失败码、Tool调用数、RAG命中率、平均耗时。
- 日志：traceId贯穿 API -> Agent -> Tool -> RAG -> 审批。

## 7. 技术方案

### 7.1 架构总览
采用“Spring Boot编排内核 + LangChain4j执行层 + SSE流式回传 + 事件总线同步UI”的模式：

- **编排层**：`AgentApplicationService` 演进为 `AgentOrchestrator`（或同级服务）。
- **模型层**：通过项目模型策略选择具体 `ChatLanguageModel`。
- **工具层**：插件安装信息映射为可调用Tool集合（执行型/拦截型）。
- **记忆层**：RAG检索结果注入系统上下文。
- **审批层**：拦截型Tool产出审批单并驱动状态机。
- **传输层**：SSE主通道输出token；WebSocket用于项目级广播事件。

### 7.2 关键模块改造

#### 7.2.1 后端
1. 新增 `AgentOrchestrator`：
   - 组装上下文（会话、章节、大纲、文风、RAG）。
   - 调用LangChain4j执行生成。
   - 分发token到 `GenerationStreamService`。
   - 处理Tool调用与异常降级。
2. `AgentApplicationService.createGeneration` 改为异步触发编排，不再立即置 `done`。
3. 引入统一状态枚举与状态机守卫（非法流转直接拒绝）。
4. `PluginApplicationService` 增加调用日志写入能力。
5. `RagApplicationService` 增加真实检索日志与召回接口。
6. 审批流程与任务状态联动：`waiting_approval <-> running/done/failed`。

#### 7.2.2 前端
1. Workbench接入 `EventSource` 订阅 `/stream`。
2. 统一状态映射：严格消费后端状态枚举。
3. 生成中展示分段token，完成后支持一键应用。
4. 审批卡与任务状态联动展示（待审批/已通过/已驳回）。

#### 7.2.3 数据与存储
1. `agent_generation_tasks` 补充字段：`model_config_id`、`token_usage_json`、`cost_json`、`trace_id`。
2. `plugin_call_logs` 增加 `task_id` 关联。
3. `rag_retrieval_logs` 新表（或复用日志表）记录召回详情。

### 7.3 推荐技术选型
1. **LangChain4j**：用于模型调用、Tool绑定、流式回调。
2. **SSE**：主流式通道；保持现有接口兼容。
3. **MySQL + Redis**：任务状态、幂等与短期上下文缓存。
4. **Milvus/Pinecone（二选一先落地）**：向量检索。

### 7.4 核心时序（P0）
1. 前端提交生成请求，后端创建任务（`pending`）。
2. 编排器启动任务（`running`），持续推送token到SSE。
3. 若触发拦截型Tool，任务转 `waiting_approval` 并创建审批单。
4. 审批通过后继续执行并完成（`done`）；驳回则根据策略转 `done` 或 `failed`。
5. 用户点击应用，任务转 `applied`，同步编辑区。

### 7.5 兼容与迁移
1. 保留现有REST接口路径，新增字段向后兼容。
2. 前端保留短期轮询兜底开关，稳定后下线。
3. 历史任务按旧状态映射至新状态展示。

## 8. 接口与事件契约（一期约束）

### 8.1 任务状态枚举（统一）
`pending | running | waiting_approval | done | applied | failed | cancelled`

### 8.2 SSE事件
- `generation.started`
- `generation.token`
- `generation.tool_call`
- `generation.waiting_approval`
- `generation.done`
- `generation.failed`

### 8.3 错误码建议
- `AGENT_CONTEXT_BUILD_FAILED`
- `AGENT_MODEL_CALL_FAILED`
- `AGENT_TOOL_TIMEOUT`
- `AGENT_APPROVAL_REQUIRED`
- `AGENT_STATE_TRANSITION_INVALID`

## 9. 测试与验收方案

### 9.1 测试范围
1. 单测：状态机、上下文组装、Tool路由、审批分支。
2. 集成测试：生成->流式->审批->应用全链路。
3. 前端E2E：流式渲染、断连恢复、审批交互、编辑器应用。

### 9.2 验收用例（核心）
1. 无插件/无审批场景：可稳定流式完成并应用。
2. 插件调用场景：Tool成功与超时降级均可完成任务。
3. 审批场景：待审批卡出现、审批后数据落库与UI同步。
4. 状态一致性：前后端展示与后端实际一致。

### 9.3 验收指标
- 全链路成功率 >= 95%
- 审批闭环成功率 >= 99%
- 关键API P95 响应时间满足基线
- 无P0级数据一致性缺陷

## 11. 风险与应对
1. **模型/工具不稳定**：设置超时、重试、降级文案与兜底生成。
2. **SSE连接质量波动**：增加重连策略和任务恢复查询接口。
3. **审批阻塞影响体验**：允许“先继续写作，后处理审批”的异步策略。
4. **安全改造影响历史数据**：提供密钥迁移脚本与回滚预案。

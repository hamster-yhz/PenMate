# PenMate Backend Java 注释全量改造计划

## 1. 目标与范围

- 仅覆盖 `penmate-backend/src/main/java` 下全部 Java 类型。
- 覆盖对象包括：`class`、`interface`、`enum`、`record`、DTO、Mapper、Repository、Controller、Application Service、Domain Model。
- 处理规则：
  - 对有业务逻辑的方法体（Controller/ApplicationService/DomainService/RepositoryImpl）补充详细业务流程与关键调用步骤注释。
  - 对 Mapper/DTO/record 仅写用途说明与字段解释。
  - 对现有模板化、泛化、不可读注释全部替换或重写，不做增量修补。

## 2. 注释规范

### 2.1 类级注释

每个类型统一使用可读的职责导向描述，至少包含：

1. 该类型在分层中的职责与边界。
2. 主要输入输出或协作对象。
3. 关键约束（幂等性、事务边界、安全上下文、状态机约束等，如适用）。

禁用内容：`XXController。`、`处理业务请求。`、`查询列表数据。` 等模板句。

### 2.2 方法级注释（详细流程，仅业务方法）

对业务方法按固定结构编写：

1. **业务目的**：该方法解决什么业务问题。
2. **流程主线**：按时序列出步骤（校验 -> 组装命令 -> 调用服务 -> 持久化/发布事件 -> 返回）。
3. **关键调用**：标注核心调用点和调用原因。
4. **异常与分支**：说明关键失败分支与异常语义。
5. **副作用**：说明状态变更、外部通知、日志/审计写入。

### 2.3 模型与数据结构注释

对 Domain Model、DTO、record 的每个字段补充：

1. 业务语义。
2. 取值约束与可空性。
3. 单位或格式（时间、枚举值、JSON 结构、对象键等）。
4. 与上下游字段映射关系（必要时）。

## 3. 分层改造策略

### 批次 A：接口层与应用层

- `interfaces/api/**`：Controller 方法注释改写为接口语义 + 调用链说明。
- `application/**`：编排、路由、状态机、命令构造流程注释细化。

### 批次 B：领域层

- `domain/**/model/**`：字段逐一解释。
- `domain/**/repository/**`、`domain/shared/service/**`：职责与契约注释明确。

### 批次 C：基础设施层

- `infrastructure/persistence/**`：RepositoryImpl 方法补充 SQL/Mapper 调用意图与写入语义。
- `infrastructure/realtime/**`、`infrastructure/security/**`、`infrastructure/llm/**`：事件推送、安全加解密、模型网关调用流程说明。

### 批次 D：配置与入口

- `interfaces/config/**`、`PenmateBackendApplication`：配置意图、过滤链/切面行为说明。

## 4. 模板注释清理清单

重点替换以下已识别高频模板语句：

- `处理业务请求。`
- `查询列表数据。`
- `查询详情数据。`
- `创建业务数据。`
- `更新业务数据。`
- `删除业务数据。`
- `发布业务状态。`

执行要求：出现即改，且改为上下文相关的可读注释。

## 5. 执行步骤

1. 建立文件清单并按分层分批处理，避免跨层混改。
2. 每个文件先完成类级注释，再处理方法级，再处理字段级。
3. 对方法体内关键调用前补充行内注释，强调业务意图而非语法解释。
4. 同文件内统一术语，确保命名与注释一致。
5. 批次完成后进行术语与模板词回归扫描。

## 6. 验收标准

1. `src/main/java` 全量类型均有类级注释。
2. 业务方法具备完整流程注释，包含关键调用步骤。
3. 模型类与 DTO/record 字段解释完整，无空白字段说明。
4. 不再存在模板化宽泛注释（如“处理业务请求”）。
5. 注释内容与代码行为一致，不出现过时描述。

## 6.1 严格验收闸门

每批次与最终交付均需同时通过以下闸门：

1. **覆盖闸门**：批次内文件 100% 完成逐文件勾检。
2. **模板清零闸门**：目标目录中禁用模板语句检索结果为 0。
3. **字段完整闸门**：模型类与 DTO/record 字段说明无遗漏。
4. **流程完整闸门**：业务方法均包含目的、流程、关键调用、异常分支、副作用。
5. **一致性闸门**：术语与注释风格与术语表一致。

任一闸门不通过，视为该批次未完成，不进入下一批次。

## 6.2 逐文件勾检表

按目录维护勾检表，执行时逐行勾选。建议在实施阶段创建并维护文件：

- `plans/checklists/A-interfaces-application.md`
- `plans/checklists/B-domain.md`
- `plans/checklists/C-infrastructure.md`
- `plans/checklists/D-config-entry.md`

单文件勾检模板：

```markdown
- [ ] 文件：<relative-path>
  - [ ] 类级注释清晰且非模板化
  - [ ] 业务方法流程注释完整（如适用）
  - [ ] 关键调用步骤注释齐全（如适用）
  - [ ] 字段说明完整（模型/DTO/record 适用）
  - [ ] 模板语句清零
  - [ ] 术语一致性复核通过
```

## 6.3 批次完成定义

批次完成必须满足：

1. 批次勾检表全部勾选完成。
2. 批次范围模板语句回归扫描为 0。
3. 抽样复核至少覆盖：Controller、ApplicationService、RepositoryImpl、Model/DTO/record 四类文件。
4. 抽样复核发现问题已回写并重新通过闸门。

## 6.4 全量完成定义

全量完成必须满足：

1. 四个批次勾检表均完成。
2. `src/main/java` 全域模板语句检索为 0。
3. 随机抽查不少于 15 个文件，均满足注释规范。
4. 最终复核记录在 `plans/` 下归档，作为交付依据。

## 7. 风险与控制

- 风险：批量改注释易出现术语不一致。
  - 控制：先维护统一术语表，再分批应用。
- 风险：流程注释过长影响可读性。
  - 控制：优先“目的 + 主线 + 关键调用”，避免重复代码字面描述。
- 风险：遗漏字段说明。
  - 控制：以类型字段列表逐个勾检，批次结束做回归扫描。

## 8. 交付物

- 本计划文档（当前文件）。
- 批次逐文件勾检表（`plans/checklists/*.md`）。
- 最终复核记录（建议：`plans/comment-review-report.md`）。
- 后续代码改造提交应满足本计划的范围、规范、步骤与验收项。
